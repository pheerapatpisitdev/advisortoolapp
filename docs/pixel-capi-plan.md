# แผน Meta Pixel และ Conversions API

สถานะ: แผนอย่างเดียว ยังไม่เขียนโค้ด
อ้างอิงโค้ดที่มีอยู่และเอกสาร Meta (Conversions API, การตัดเหตุการณ์ซ้ำด้วย event_id)
แอปใช้ Graph `v23.0` อยู่แล้วใน `src/lib/ads/sync.ts` แผนนี้ใช้เวอร์ชันเดียวกัน

## สิ่งที่มีอยู่ และสิ่งที่ยังไม่มี

มีแล้ว: webhook Messenger จับ `ad_id` จาก referral, บันทึกลงบทสนทนาและลีด, หน้า `/admin/ads` อ่านผลใช้จ่ายอย่างเดียวด้วย `ads_read`
ยังไม่มี: Pixel บนเว็บ, การส่งเหตุการณ์กลับไปหา Meta, การดึงฟอร์ม Lead Ads

Pixel มองไม่เห็นคนที่ทักใน Messenger หรือ LINE เพราะไม่มีเบราว์เซอร์ของเรา
แอดที่เปิดแชทต้องส่งจากเซิร์ฟเวอร์ตอน webhook เท่านั้น

## 1. วาง Pixel ที่ไหน

`src/app/layout.tsx` เป็น server component อยู่แล้ว ไม่ยัดสคริปต์ Facebook ลงไฟล์นี้ตรง ๆ
เพิ่มคอมโพเนนต์ลูกที่เป็น client เช่น `src/components/meta/Pixel.tsx` แล้วเรนเดอร์จาก root layout

โหลดสคริปต์หลังเพจพร้อม และยิง PageView เมื่อ path เปลี่ยน เพราะ App Router ไม่รีโหลดทั้งหน้า
ไม่ใส่ใน `/admin` และ `/studio` คนที่เข้าสองเส้นนี้คือทีมงาน ไม่ใช่ผลของแอด
เส้นทางลูกค้าที่ใส่: `/`, หน้าคำนวณ (`/lifeprotect`, `/ihealthy-ultra`, `/fhc` และแบบอื่น), `/login` ไม่จำเป็น

Pixel id มาจาก `NEXT_PUBLIC_META_PIXEL_ID` ถ้าไม่มีค่า ไม่โหลดสคริปต์

## 2. เหตุการณ์ที่ส่ง

| เหตุการณ์ | เมื่อไหร่ | ทาง |
| --- | --- | --- |
| PageView | เปิดหน้าลูกค้า | Pixel |
| Contact | เริ่มแชทบนเว็บครั้งแรกของเซสชัน | Pixel และ CAPI |
| Lead | มีบทสนทนาใหม่จาก Messenger ที่มาจากแอด หรือมีฟอร์มถูกส่ง (`form_sent_at`) | CAPI จากเซิร์ฟเวอร์ |
| Quote | คำนวณแล้วได้ราคา (`priced_at`) หรือมีการสร้างใบเสนอราคา | CAPI และ Pixel ถ้าเกิดบนเว็บ |

LINE ยังไม่มี `ad_id` จาก Meta อย่าส่งเป็น conversion ของ Facebook
อย่าส่ง PageView จาก webhook

ชื่อเหตุการณ์ใช้ชุดมาตรฐานของ Meta คือ PageView, Contact, Lead ไม่คิดชื่อใหม่

## 3. Conversions API

เพิ่ม `POST /api/meta/events` สำหรับเหตุการณ์ที่เกิดบนเว็บ
เบราว์เซอร์ยิง Pixel พร้อม `eventID` แล้วเรียก route นี้ด้วย `event_id` ตัวเดียวกัน
เซิร์ฟเวอร์โพสต์ไปที่ `https://graph.facebook.com/v23.0/{PIXEL_ID}/events`

เหตุการณ์จาก Messenger ไม่ผ่าน route นี้ เรียกตัวส่งเดียวกันจากตัวบันทึกบทสนทนาหลังรู้ `ad_id` แล้ว
`action_source` ของเว็บคือ `website` ของ Messenger คือ `business_messaging`

แฮชก่อนส่ง ตามเอกสาร Meta: อีเมลตัวเล็กและตัดช่องว่าง, เบอร์เหลือแต่ตัวเลข แล้ว SHA-256
ไม่ส่งอีเมลหรือเบอร์ดิบไปในล็อก
แชทแรกมักยังไม่มีอีเมล ส่งเท่าที่มี อย่าสร้างข้อมูลปลอม

ตัดซ้ำ: `event_id` ฝั่งเซิร์ฟเวอร์ตรงกับ `eventID` ฝั่ง Pixel และชื่อเหตุการณ์เดียวกัน ภายใน 48 ชั่วโมง Meta จะทิ้งอันที่ซ้ำ
Messenger ไม่มี Pixel คู่กัน จึงไม่ต้องตัดซ้ำ ใช้ `event_id` คงที่จาก id บทสนทนาเพื่อกัน webhook ส่งซ้ำ

โทเค็น CAPI อยู่ฝั่งเซิร์ฟเวอร์เท่านั้น ไม่ใส่ในคอมโพเนนต์ลูก

## 4. ผูกกับ CRM และ ad_id

เว็บ: อ่านคุกกี้ `_fbp` และ `_fbc` ส่งใน `user_data` เพื่อให้ Meta จับคู่คลิก
Messenger: ส่ง `custom_data` ที่มี `ad_id` จาก referral ที่บันทึกอยู่แล้ว และใช้ id บทสนทนาเป็น `external_id` หลังแฮช
ไม่เขียนทับ `ins_ad_daily` ตารางนั้นคือตัวเลขใช้จ่ายที่ดึงมา คนละทางกับการส่ง conversion กลับ

เมื่อมีอีเมลหรือเบอร์ในบทสนทนาตอนหลัง ค่อยส่ง Lead อีกครั้งพร้อมข้อมูลที่แฮชแล้ว โดย `event_id` ใหม่เฉพาะตอนข้อมูลครบ ไม่ใช้ id เดิมของแชทแรก

## 5. ค่าที่ต้องตั้ง และขั้นตอนบน Meta

ตัวแปรใหม่

| ตัวแปร | ที่อยู่ |
| --- | --- |
| `NEXT_PUBLIC_META_PIXEL_ID` | เบราว์เซอร์ |
| `META_CAPI_ACCESS_TOKEN` | เซิร์ฟเวอร์เท่านั้น |
| `META_TEST_EVENT_CODE` | ชั่วคราวตอนทดสอบ เอาออกเมื่อขึ้นจริง |

ใส่ใน `.env.local` และบน Vercel ทั้ง Production, Preview, Development
ไม่ต้องขอ `ads_management` สิทธิ์อ่านโฆษณาเดิมไม่เกี่ยวกับงานนี้

บน Meta

1. Events Manager สร้าง Pixel ของพอร์ตโฟลิโอ Luckyplanner ถ้ายังไม่มี
2. สร้าง access token ของ Conversions API ผูกกับ Pixel นั้น
3. เปิด Test events ใส่ `META_TEST_EVENT_CODE` แล้วยิง PageView กับ Lead หนึ่งครั้ง
4. เอา test code ออกก่อนใช้งานจริง
5. ในแอดที่เปิดเว็บ ตรวจว่า URL มี `fbclid` เพื่อให้คุกกี้ `_fbc` เกิด
6. แอดที่เปิด Messenger จะได้ผลจาก CAPI อย่างเดียว ไม่ต้องติด Pixel ที่ปลายทาง

## สิ่งที่แผนนี้ไม่ทำ

ไม่สร้างแคมเปญ ไม่ปรับงบ ไม่ดึงฟอร์ม Lead Ads
ไม่ยิง Pixel ในหลังบ้านและสตูดิโอ
